# 盐城中学 · 盐中之声 每日点歌系统

Cloudflare Pages + Pages Functions + D1，无需服务器、无需付费、无需构建步骤。

> **前端改动约定**：三个原有页面的 `<style>` 块与原版**逐字节相同**，CSS 类名与视觉风格未变。
> 所有改动都集中在 `<script>` 逻辑里，DOM 只做了用户逐条批准的新增
> （主页的公告区、两个列表容器；点歌页的试听按钮；后台登录页移除动态口令输入框、加注册入口）。
> 这条约定由测试硬性守住，见文末「测试」一节。

## 二、这次修掉的安全问题

### 1. 存储型 XSS（最高危，群友就是靠它改掉管理员密码）

**原因**：`admin.html` 用 `innerHTML` 拼接 `${s.title}`，歌名里的
`<img src=x onerror=...>` 会被当 HTML 执行；而登录后密码被明文写进 `sessionStorage`，
XSS 一执行就能读走。

**修复**：
- `index.html` / `admin.html` / `vote.html` 的 `<script>` 顶部加 `escapeHtml()`，
  所有来自后端的文本（歌名、歌手、分类、班级名、黑名单关键词、举报原因、公告、试听结果……）
  逐个包裹；数值字段（id、票数、班级号、分类号）一律经 `safeInt()` 转整数，
  堵死 `onclick="action(1);alert(1)//"` 这类从"数字字段"打进来的注入。
- 需要传参给 `onclick` 时改用 `data-*` 属性 + `dataset` 读取，**不把文本拼进 JS 字符串**
  （歌名里的反斜杠可能转义掉引号造成注入）。
- 入库前在 `_lib/validate.js` 收敛为安全纯文本（纵深防御）。

**关于 CSP 的实话**：`_headers` 提供了 `Content-Security-Policy`（`default-src 'none'`、
`frame-ancestors 'none'`、`object-src 'none'` 等）。但因为按约定保留了页面内联 `<script>`
与 `onclick` 属性，`script-src` **必须放开 `'unsafe-inline'`**，所以它只能挡住"外链注入"，
**挡不住页面内联脚本注入**——真正的防线是上面的转义。这一点在 `_headers` 注释里也写明了，没有粉饰。

> 顺带修掉一个此前没人发现的 bug：原主页 JS 往 `pendingList` / `approvedList` 写内容，
> 但 HTML 里只有 `rankList`，`switchMobileTab()` 引用的元素也全不存在，
> 所以主页必然抛 `TypeError`、"加载中…"永不消失。现已按约定补上这两个容器。

### 2. 明文口令

- `admins` / `classes` 的 `password` 列改存 **PBKDF2-SHA256（随机盐 + 10,000 次迭代）**，
  自描述格式 `pbkdf2$sha256$迭代$盐$摘要`。
- **旧数据无需手工迁移**：首次登录自动识别旧的明文/弱哈希，验证通过后立刻写回哈希。
- 为什么不是裸 SHA-256：SHA-256 是"快哈希"，每秒能算上亿次，存口令等于不设防。
- 迭代次数取 10,000 是受平台硬约束：免费套餐**单次请求 CPU 上限 10ms**，
  实测 25,000 次要 4.75ms、50,000 次要 9.17ms 已越线；10,000 次约 3ms，
  即使管理员改密走"校验 + 重新哈希"两次也只有约 6ms。
  升级付费套餐后改 `_lib/crypto.js` 里的 `PBKDF2_ITERATIONS` 即可，旧口令会自动按新成本重哈希。

### 3. 鉴权形同虚设

| 原问题 | 现状 |
|---|---|
| `admin-list.js` 无任何认证，任何人可读全部内部数据 | 要求管理员会话，未登录返回 401 |
| `admin-settings.js` 的 GET 无认证，任何人可读黑名单 | 同上 |
| `vote.js` **只检查口令字段非空，从不校验口令是否合法** | 必须有有效班级会话；`class_id` 取自服务端 |
| 后台写接口用 `WHERE password = ?` 当权限校验 | 统一校验管理员会话 + 角色 |
| `admin-login` 登录成功不签发任何会话 | 登录签发 12 小时会话 |
| 登录接口无失败限制 | 按 IP 限流（登录 15 分钟 10 次） |
| `rank.js` 只验证"口令存在"，不校验属于哪个班级 | 会话只用来证明"你是通过口令进来的学生"；`class_id` 不再由客户端传入。见下方「多口令的语义」 |
| `status` 参数未做白名单，可读回收站 | 只允许 `approved` / `pending` |

**会话令牌通过 HttpOnly Cookie 下发**，不放进响应体、不进 `sessionStorage`。
这一点是对原始需求的刻意调整：群友正是靠 XSS 读 `sessionStorage` 里的密码才改掉了管理员账号。

### 4. 防刷票

- 查重从 `IP + User-Agent` 改为**设备指纹（7 天）**，并叠加同 IP 限流。
- **"换 UA 即重置"已失效**：UA 不再参与查重。
- 指纹采集 UA、平台、语言、时区、屏幕、CPU 核数、`devicePixelRatio`、Canvas 与 WebGL 差异，
  本地 SHA-256。**刻意不使用 localStorage / Cookie**，清缓存不会重置。
- 没把 IP 写进查重条件：校园网是同一出口 IP，若作为等值条件，
  **同班第二个同学就点不了歌**。IP 现在只用于限流。
- 并发穿透一并修掉：检查与写入合并成单条原子 SQL。

### 5. 其他

| 问题 | 修复 |
|---|---|
| 班级口令放在 URL 查询串里（会进访问日志） | 改用会话 Cookie |
| 黑名单 SQL 的 `AND`/`OR` 优先级写错，过期时间失效 | 加括号修正 |
| 黑名单 `LIKE` 方向反了，歌手名后加一个字符即可绕过 | 改用 `instr()` 字面包含 |
| `upvote.js` **根本不存在**，主页"投票"按钮实际是 404 | 补上接口 + 每班每首只能投一次的唯一约束 |
| `category_id` 可由客户端随意指定 | 校验必须真实存在于 `categories` |
| 页面引用的两张图**实际不存在** | 补齐 `school-badge.png` / `radio-logo.png`（HTML 一个字没改，图片就正常了） |

## 三、功能说明

### 多口令的语义（这里踩过坑，重要）

**多个班级口令是「多把进同一系统的钥匙」，不是多租户。全校共用同一份榜单。**

这一点曾经做错过：早期版本让榜单按"登录用的那个班级口令"过滤，结果是——
你新加一个班级口令、用它登录后，**榜单变成空的**，因为历史歌曲都挂在第一个班级名下。

现在：
- 榜单查询**不按 `class_id` 过滤**，任何口令登录看到的都是同一份榜单。
- 点歌查重是**全校范围**的：不同班级点同一首歌也算重复，会提示"已经在队列里了"。
- 投票与举报也是全校范围：别人班点的歌你一样能投、能举报。
- 歌曲记录里的 `class_id` 只用于标注"这是哪个班点的"，在后台能看到，不参与可见性判断。

### 多管理员系统

- **高级管理员**（`role='super'`）：就是你的 `admin` 账号。能生成动态口令、管理其他管理员、
  改班级口令与分类权重。
- **普通管理员**（`role='admin'`）：通过动态口令注册，能审核歌单、维护黑名单、发公告；
  **不能**管理其他管理员，也不能改班级口令与分类权重。

**怎么拉人进来**：用高级管理员登录 → 系统设置 → 「生成动态口令」→
填可用次数与有效天数 → 生成后**立刻复制**（明文只显示这一次），
把口令或"带口令的注册链接"发给对方 → 对方打开 `/register.html` 填账号密码与口令即可注册。

> 动态口令在数据库里只存 SHA-256 摘要，因此生成后无法再查。这是刻意的：
> 邀请码能换来管理员权限，明文落库等于给数据库泄露多加一条利用路径。
> 如果弄丢了，作废重新生成即可。

### 公告区

主页最上方显示（只显示上架的），管理员在「系统设置 → 发布公告」里增删改与上下架。
公告内容保留换行。

### 回收站 ≠ 黑名单

这两个是完全独立的东西，界面上也分开写了：

- **回收站**：`songs` 表里 `status='rejected'` 的歌曲。可以逐首**恢复**或**彻底删除**，
  也有**一键清空回收站**。彻底删除会同时清掉它的举报与投票记录。
- **黑名单**：`banned_items` 表，是"禁止再提交某个歌手 / 某个歌名"的**规则**，
  不包含任何歌曲记录，也不会删除已有歌曲。支持 30 / 90 / 365 天或长期，到期自动解禁。

### 班级口令的查看与分发

班级口令是要发到各个班去的，所以管理员**必须随时能查到**"高一(3)班的口令是什么"。
只存 PBKDF2 哈希的话管理员自己也拿不回来，因此口令存两份：

| 列 | 内容 | 用途 |
|---|---|---|
| `password` | 加盐 PBKDF2 哈希 | 登录校验，不可逆 |
| `password_encrypted` | **AES-GCM 密文** | 仅用于管理员在后台查看与复制 |

密钥由 `AUTH_PEPPER` 派生，**存在环境变量里而不是数据库里**，
所以只拿到数据库（没有环境变量）依然解不开，比直接存明文强得多。

- 只有**高级管理员**能看到口令；普通管理员拿到的是"仅高级管理员可见"。
- 后台「班级口令列表」每行都有口令和「复制」按钮，勾选可以批量删除。

> ⚠️ **不要随意更换 `AUTH_PEPPER`。** 查找索引和这份密文都由它派生，
> 换了之后所有已有班级口令会失效、旧密文也解不开。
> 万一换了：管理员仍能登录（管理员登录不依赖查找索引），
> 到后台把班级口令**逐个重设**或**批量重新生成**一遍即可恢复。

### 一键批量生成班级口令

系统设置 → 「一键批量生成班级口令」：填前缀（如「高一」）与序号范围（如 1–20），
选"每班一个随机口令"或"所有班共用一个口令"，一次生成到位，不用一个个加。
生成完会把 `班级名 + 口令` 的清单放在一个文本框里，点「复制全部口令」就能贴到群里分发。

> **随机口令只显示这一次**（库里只有哈希）。丢了就在列表里逐个"修改口令"重置。

**为什么是前端逐个调用而不是后端一次循环**：服务端每个班级要跑一次 PBKDF2（约 3ms CPU），
一次建 20 个就是 60ms，会直接撞上免费套餐"单次请求 10ms CPU"的上限而被掐断。
拆成 20 个请求后每个都在预算内，代价只是多几次网络往返。

### 年级 / 人数 / 投票上限

班级多了两个管理员可填的字段：**年级**（如「高一」）与**人数**。

- 后台「班级口令列表」**按年级分组**展示，每组显示"共 N 个班 · 已填 M 个班共 X 人"；
  60 个班平铺一列根本找不到人。
- 每个班有「改年级/人数」按钮；批量生成时也能一次填好年级与每班人数。
- 系统会把所有班级的人数**汇总成全校总人数**，显示在「投票上限」卡片里。

**投票上限的规则：超过上限的那部分票不计入票数。**

- 在后台「投票上限（超出部分不计入）」里填一个数字，点「保存上限」；
  可以点「填入汇总人数」直接把班级人数汇总结果填进去。
- 填 **0 表示不限制**。
- 生效方式：票照收、数据库里的原始票数不变，但**学生端显示的票数与正式榜排序都用封顶后的值**。
  例如上限 900、某首歌实际 1200 票，学生看到的是 900 票；接口里仍带
  `votes_raw: 1200` 与 `votes_capped: 1` 供排查。
- 这样即使有人刷票，数字也不会出现"比全校人数还多"这种不可能的值。

### 调试模式（用管理员身份在学生端点歌）

在**主页的班级口令输入框**里输入：

```
管理员账号 空格或冒号 管理员密码
```

例如 `admin:admin888` 或 `admin admin888`。通过后即进入调试模式：

- **点歌不限次数**，不占用"每人每周一次"的额度；
- **不查重**，同一首歌可以反复提交，方便测试；
- 提交的歌会标记 `is_debug=1`，在后台审核列表里显示紫色的**「调试模式」**；班级显示为"调试"而非编号；
- **与已有正式歌曲同名同歌手的调试歌曲不会显示在审核列表里** —— 调试时反复提交同一首歌，不隐藏会刷屏。不重复的调试歌曲正常显示。
- 黑名单规则仍然生效，方便顺便验证过滤是否工作。

调试会话有效期 2 小时；和普通学生会话一样走 HttpOnly Cookie，不影响后台登录态。

### 试听

排行榜页（每首歌）、点歌页（「🔍 搜索歌曲」与「▶ 先试听一下」）、以及后台审核列表都有试听。
搜到之后可以直接「选这首」把歌名歌手填进表单，避免手打错字。

**试听结果用独立的「候选面板」呈现，和榜单卡片明显区分**：左侧品牌色竖条 + 淡蓝底 +
标题与数量（如「🎧 试听候选 · 3 个」）+ 右上角固定的**「收起 ▲」**按钮，
并注明"以下为搜索到的候选版本，不是榜单上的歌曲"。不再用和 `.rank-card` 一样的白色卡片，
也不用靠"再点一次试听"去猜怎么关。

**音源选型做过了实测**（参考开源项目 [VoiceHub](https://github.com/laoshuikaixue/VoiceHub) 的
`musicSources.ts`，它是自托管 Nuxt 全栈、自带服务器，架构与我们不同，但音源清单可借鉴）：

| 音源 | 实测结果 |
|---|---|
| `api.qijieya.cn/meting/` | ✅ 可用，302 跳转到可播放音频（完整歌曲） |
| `api.injahow.cn/meting/` | ✅ 可用，同上 |
| `itunes.apple.com` | ✅ 可用，官方 30 秒试听，无需 key、支持 Range |
| `api.ygking.top` | ❌ 域名已失效 |
| `music-api.gdstudio.xyz` | ❌ 连接超时 |
| `api.bilibili.com` | ❌ 412，需要 WBI 签名，必须自建服务 |
| `api.vkeys.cn` | ⚠️ 可达但返回业务错误 |

**策略**：默认 `auto` —— Meting 与苹果**并行**发起，优先采用 Meting（完整歌曲），
拿不到就自动用苹果官方 30 秒试听兜底。任何一家挂掉都不会让功能失效，
而且**不配任何环境变量就能用**。

> **SSRF 防护**：客户端**永远不能指定上游地址**，只能传关键词或歌曲 id，
> 上游地址由服务端决定。歌曲 id 带音源前缀（`mt-xxx` / `ap-xxx`），
> 播放时不必猜测该用哪家，也避免两家的数字 id 撞车。代码里有对应的回归测试。

## 五、免费套餐相关的两个关键优化

1. **`_routes.json` 只让 `/api/*` 走 Functions。**
   没有它时，**每一个图片 / CSS / JS 请求都会消耗一次 Functions 调用额度**（免费 10 万次/天）。
   加上之后静态资源走无限免费的静态通道，这是"长期稳定运行"的关键一环。
2. **PBKDF2 迭代次数按 10ms CPU 上限调校**，批量生成班级口令改成前端逐个调用，
   都是为了避免撞上 CPU 上限。`_harness/bench.mjs` 可随时重新测量。

## 六、已知问题与限制

1. **SQL 脚本不可重复执行**（`ALTER TABLE` 无 `IF NOT EXISTS`），第二次跑会在该行报错，属正常。
2. **管理员口令目前仍是已公开的弱口令 `admin888` / `yczx2026`**，请登录后立刻改掉。
3. **CSP 的 `script-src` 因保留内联脚本而必须放开 `'unsafe-inline'`**，挡不住内联脚本注入；
   当前主要防线是转义。收紧的前提是脚本外链化，需要你点头。
4. **无账号体系时"每人每周一次"无法做到绝对**，换设备换网络仍可再点一次；
   指纹方案把成本抬高了很多，且不误伤同校园网的其他同学。
5. **试听依赖第三方音源**：Meting 是公开代理，可能随时失效（失效时自动降级到苹果官方 30 秒试听）。
   苹果的 `cn` 商店不通过接口提供歌曲，所以默认用 `hk`，歌名可能是繁体。
6. **试听会消耗 Functions 调用额度**（音频经代理转发，每段 Range 请求算一次调用）。
   按 300 人每天 3 次试听估算约 2700 次/天，远低于 10 万次上限。
7. **本机环境无法验证线上部署结果。** 交付前已用本地 D1 兼容测试脚手架跑通
   **138 项测试**（含真实执行三份迁移 SQL、CSS/DOM 未改动的逐字节比对、XSS 载荷渲染测试、
   音源代理的 SSRF 回归、提权回归、权限边界、21 个 JS 文件语法检查），
   但生产环境部署是否变绿、`vote.yzstu.top` 是否正常，需要你在控制台确认。
